# ИИ-консультант для чата Softline Store

Хакатон ИИкузница, трек "Клиентские сценарии", задача "Агент поддержки" (заказчик: Софтлайн).

Агент ведет покупателя в чате store.softline.ru от вопроса до черновика КП: находит названный продукт и доводит до конкретной лицензии, подбирает решение под задачу, отвечает по справке магазина. Менеджеру остается то, что требует полномочий (скидки, госзакупки, жалобы), и приходит это готовой карточкой: кто клиент, что ему нужно, какие позиции и на какую сумму.

- Чат покупателя: https://ai-support.emagi.co
- Экран оператора: https://ai-support.emagi.co/admin (без ключа открыт на чтение, контакты клиентов скрыты)
- Показ проверки цен: https://ai-support.emagi.co/proof
- Питч и сценарий показа: [docs/pitch.md](docs/pitch.md)
- Спринт: 26.11.2026 10:00 МСК - 28.11.2026 10:00 МСК

### Что проверить за пять минут

1. **Подбор.** В чате: "Нужно защитить почту и файлы на 50 сотрудников, что посоветуете?" Агент уточнит недостающее, предложит варианты из каталога с описанием и ценой на 50 мест.
2. **КП.** Там же: "Сделайте КП на ООО Ромашка, ИНН 7701234567, КПП 770101001". В чате появится ссылка на PDF по шаблону заказчика; суммы и НДС в нем посчитал код.
3. **Менеджер.** "Нужна скидка 15%": агент сам дает 5%, остальное передает менеджеру. Обращение появляется на экране оператора готовой карточкой и уходит в Telegram менеджеров; ответ менеджера клиент видит в том же чате.
4. **Проверка цен.** Страница `/proof`: модель называет цену, которой нет в каталоге, код не выпускает ее к клиенту.
5. **Экран оператора.** Журнал диалогов с шагами агента, токенами и рублями, экономика с допущениями, 63 диалога проверочного прогона.

Ключ оператора для полного доступа к экрану указан в описании решения в личном кабинете участника.

## Покрытие задачи

| Требование | Как закрыто |
|---|---|
| Клиент называет продукт ("нужен MDaemon Standard"): сверить версии по фиду, задать уточняющие вопросы | `search_products` находит продукт с опечатками и разговорными названиями и сразу отдает варианты лицензий, если продукт найден однозначно. `get_product` сужает варианты фильтрами; поле `clarify` говорит, что уточнить (пользователи, срок, новая или продление, тип организации), `facets` показывает, какие значения есть в каталоге. Редакции "Standard" у MDaemon в фиде нет: агент говорит это прямо и показывает то, что есть |
| Клиент не знает, что нужно: выяснить требования и подобрать | до трех вопросов по одному за сообщение (задача, объем, инфраструктура), затем категории и продукты каталога, два варианта с обоснованием по описаниям продуктов |
| Вопросы о продуктах и магазине | параметры вариантов из фида, описание продукта со страницы магазина (вкладка "Описание": для чего продукт и чем отличается от соседних) и `kb_search` по справке Softline и служебным страницам магазина, ответ со ссылкой на страницу |
| "А есть ли российский аналог?" | `find_analogs`: ветки "(Импортозамещение)" из фида, номер реестра отечественного ПО из фида, справочник российских вендоров |
| Черновик КП по шаблону (необязательное) | `make_quote`: PDF по шаблону заказчика, графа "Заказчик" с названием, ИНН и КПП, суммы и НДС считает код, пометка "черновик, проверяет менеджер" |
| Передать вопрос из чата менеджеру и обратно в удобном канале (заказчик на брифе назвал это плюсом) | карточка обращения и черновик КП приходят в Telegram менеджеров; менеджер отвечает на карточку реплаем, клиент видит ответ в чате сайта через несколько секунд; кнопки "Взять в работу" и "Вернуть агенту" |
| Сложный случай уходит оператору, клиент может позвать его сам | правило заказчика в инструкции: кого можно обслужить здесь и сейчас по каталогу и справке, обслуживает агент; тендер, продукт вне каталога, цена по запросу, жалоба уходят менеджеру. В чате есть кнопка "Позвать менеджера": обращение заводит код, модель для этого не вызывается |
| Скидка: агент сам дает до 5%, остальное решает оператор | параметр `discount_percent` в `calc_total` и `make_quote`; потолок держит код, а не модель. Больше 5%, отсрочка и постоплата уходят менеджеру, клиенту прямо говорится, что отсрочки в магазине нет |
| Персональные данные не уходят за границу (152-ФЗ) | почта, телефон, ИНН и КПП клиента заменяются метками до отправки в модель; настоящие значения код сам кладет в обращение и КП. Модель меняется настройкой, в том числе на российскую или в своем контуре |
| Экономить время менеджеров | агент закрывает диалог сам либо передает обращение карточкой, которую собирает код: срочность, срок реакции, клиент, запрос, позиции, сумма, ссылка на черновик КП |
| Каталог обновляется автоматически | сервер раз в сутки скачивает фид с адреса магазина и подменяет базу без остановки чата; обновление можно запустить кнопкой |
| Логировать вопросы и ответы, учиться на ответах менеджеров | журнал всех диалогов с шагами агента и выгрузкой в CSV; ответ менеджера на обращение виден клиенту в чате, а общий ответ становится знанием агента для следующих клиентов |

## Цифры

Финальный прогон проверочного набора: 26.11.2026, 63 диалога (150 реплик клиента), модель Claude Sonnet 5.5, каталог с живого фида магазина.

| Показатель | Значение |
|---|---|
| Диалогов прошло все проверки | 57 из 63 (90%) |
| Закрыто без менеджера (обращение менеджеру не заводилось) | 45 из 63 (71%) |
| Агент ответил сам, без сбоя и пустого ответа | 63 из 63 |
| Суммы, которых нет в каталоге, в ответах клиентам | 0. Проверка цен сработала один раз, проверка скидки ни разу |
| Черновик КП там, где его просили | 7 из 7 |
| Скидка в пределах полномочий: не больше 5%, сверх этого ничего не обещано | 5 из 5 |
| Оба примера из задачи ("нужен MDaemon Standard" и "не знаю, что нужно") | прошли все проверки |
| Вызовов модели / инструментов на реплику клиента | 3,1 / 2,1 |
| Токенов на реплику, среднее / медиана | 26 491 / 22 414 |
| Стоимость реплики / диалога на Claude Sonnet 5.5 | 4,58 / 10,90 руб. |

Как читать: "все проверки" это девять проверок кодом на каждый диалог (нужный инструмент, вопрос о недостающем параметре, передача менеджеру там, где она нужна, и только там, цены из каталога, скидка в пределах полномочий и другие). Шесть диалогов не прошли: в трех агент не задал уточняющий вопрос, которого ждал набор, в двух не завел обращение менеджеру там, где набор его ждал, в одном завел лишнее. Строка про суммы честнее, чем "цены из каталога 63 из 63": чужую сумму до клиента не пускает код, поэтому важнее, сколько раз ему пришлось вмешаться. Один раз, и это была перестраховка: агент повторил бюджет, названный клиентом ("уложиться в 22 000 руб."), в предложении со словом "цена", код вернул ответ на переписывание. Отчет и переписки каждого диалога пишет `python -m eval.run`. Эти же диалоги загружены на стенд, их видно на экране оператора.

Это восьмой прогон, на коде после независимого ревью. Седьмой прогон (до ревью) дал те же 57 из 63 и 71% без менеджера при 22 794 токенах на реплику. После ревью агент получил описания продуктов со страниц магазина и новые правила в инструкции: неизменная часть запроса выросла, реплика стала дороже на 15% (4,58 руб. против 3,97). Что это дало, набор не измеряет: он проверяет инструменты, вопросы, цены и передачу, а не глубину консультации. На живых диалогах стенда видно, что агент теперь объясняет, для чего продукт и чем редакции отличаются друг от друга.

Как изменил цифры бриф. После брифа в инструкцию агента вошли правила заказчика: продукта нет в каталоге и цена по запросу означают менеджера. Первый прогон на них показал перекос: агент заводил обращение слишком рано, без менеджера осталось 57% диалогов, а пример заказчика "нужен MDaemon Standard" ушел менеджеру с первого сообщения, хотя продукт в каталоге есть. Правило сузили: если продукт найден, а названной редакции нет, или в подборе попался вариант с ценой по запросу, агент сначала ведет подбор и предлагает менеджера, а обращение заводит, когда клиент согласился или прямо просит цену на такой вариант. Седьмой и восьмой прогоны шли на этой версии.

После прогона исправлена одна проверка набора: она не узнавала название продукта, написанное в кавычках ("«Альт Виртуализация» 11"), и браковала верный ответ. Цифры в таблице даны с исправленной проверкой, по тем же перепискам прогона; без исправления было 56 из 63.

Что прогон не доказывает: модель в прогоне работала через мост разработки (см. раздел "Модель"), токены посчитаны оценкой 3 знака на токен, время ответа модели в прогоне не измерялось. Заказчик на брифе назвал целью быструю реакцию (сейчас менеджер отвечает в среднем через 2 минуты), поэтому скорость измерена отдельно, на живых диалогах через чат стенда: медиана 6,8 секунды на реплику (см. раздел "Модель"). На прямом API время ответа не измерялось.

## Экономика

Заказчик назвал объем: около 500 обращений в чат за полгода, и подтвердил, что расход на модель 5-7 тыс. руб. за полгода его устраивает. В постановке задачи поток шире: 1000-2000 обращений в месяц по всем каналам; ниже посчитаны оба объема.

Экран оператора считает выгоду: сколько часов менеджеров снято и сколько это стоит за вычетом расхода на модель. Доля диалогов без менеджера и стоимость диалога берутся из замера стенда. Минуты менеджера на обращение взяты из оценки заказчика на брифе: порядка 30 минут там, где нужно искать и проверять по каталогу. Стоимость часа менеджера и польза карточки это допущения. Все три числа подписаны на экране и меняются там же. Там же показан расход на модель в рабочий день: заказчик просил считать в токенах и рублях за день.

Объем работы в числах прогона. Заказчик на брифе назвал цель: высвободить менеджеров на более сложные случаи; команда поддержки это 6-8 человек, кроме чата на них почта и общие ящики. 500 обращений по 30 минут это 250 часов за полгода. Агент сам закрывает 71% (45 диалогов из 63): 357 обращений из 500, или 179 часов. Остальные 143 приходят менеджеру готовой карточкой; при допущении, что карточка снимает половину времени, это еще 36 часов. Вместе 214 часов из 250. Экран оператора считает то же по диалогам стенда: кроме 63 диалогов прогона там лежат показательный диалог и живые диалоги, поэтому числа на экране немного отличаются и меняются с каждым новым диалогом.

## Ответы заказчика, учтенные в решении

С брифа 26.11.2026 (запись расшифрована целиком):

- Агент может дать скидку 5%, все остальное уходит оператору. Отсрочки и постоплаты в магазине нет.
- Сложный случай: тендер, нужны дополнительные документы, продукта нет в каталоге (Softline поставит его через менеджера). Кого можно обслужить через магазин здесь и сейчас, обслуживает агент.
- Статус заказа и закрывающие документы это простые вопросы: ответ есть в справке, клиента ведут в личный кабинет.
- Товар с ценой считается в наличии. Товар с кнопкой "запросить цену" сейчас купить нельзя, только через менеджера.
- Клиент должен иметь возможность переключиться на оператора кнопкой. Ответ менеджера клиент видит в том же чате.
- При зарубежной облачной модели персональные данные клиентов туда передавать нельзя.
- Менеджер сейчас отвечает клиенту в среднем через 2 минуты, цель задачи: быстрая реакция. На обращение, где нужно искать и проверять по каталогу, у менеджера уходит порядка 30 минут.
- Стоимость использования: сколько токенов уходит в день и сколько это стоит.
- Передача менеджеру засчитывается как плюс. Почта вне задачи: только чат.

Из чата задачи:

- Фид: https://store.softline.ru/feeds/Softline.yml.gz, полный каталог, обновляется несколько раз в сутки; агенту достаточно раз в сутки.
- Логировать все вопросы и ответы агента; агента можно дообучать на реальных ответах менеджера.
- Цена 0 в фиде: цену называет менеджер.
- Поля КП те же, что при оформлении заказа: название компании, ИНН, КПП, они идут в графу "Заказчик".
- Интеграции с сайтом, CRM и 1С не требуются, API магазина нет, готовых комплектов продуктов нет.
- Требований к модели нет. 500 обращений за полгода. Расход 5-7 тыс. руб. за полгода устраивает.

## Как это работает

```
 Чат на странице --> /api/chat --> Цикл агента (до 8 вызовов модели на реплику)
 (адрес страницы товара)             |  модель выбирает инструмент, код исполняет,
                                     |  модель получает результат и решает дальше
                                     v
   search_products  get_product  browse_categories  find_analogs     <- каталог, SQLite + FTS5
   kb_search                                                         <- справка и ответы менеджеров
   calc_total  make_quote                                            <- арифметика и PDF кодом
   handoff_to_manager                                                <- карточка обращения
                                     |
                                     v
   Проверки кодом: цены только из каталога, контакты скрыты от модели,
   предел шагов, времени и расхода, ответ клиенту при любом сбое
                                     |
                                     v
   Ответ клиенту + карточки товаров + кнопки выбора + след шагов с токенами и рублями
```

Проверки, которые не зависят от модели:

- **Цены.** Любая сумма в ответе сверяется до копейки с данными инструментов этого диалога. Сумма распознается в любом написании: с пробелами, точками и апострофами, "100 тысяч", "99К", в рублях, долларах и евро, без валюты после слов "итого" и "стоит", обе границы диапазона. Нашлась чужая сумма: ответ возвращается модели с замечанием. Не исправила: сумму вырезает код. Сумму, которую назвал сам клиент, агент может повторить, но не подтвердить как цену. Диапазон цен по всем вариантам продукта модель не получает, поэтому "от N руб." по самому дешевому чужому варианту назвать не может. Показ на живом цикле агента: страница `/proof`.
- **Арифметика.** Цену на количество и итог считает `calc_total`, сумму и НДС в КП считает `make_quote`. Модель не умножает. Деньги считаются в Decimal. Если цена варианта действует для другого объема закупки, код не поставит ее в КП на названное количество.
- **Контакты клиента.** Почта и телефон из сообщения клиента в модель не уходят: вместо них метки. Настоящий контакт код подставляет в обращение и в КП сам.
- **Пределы.** Не больше 8 вызовов модели на реплику, повтор того же вызова не исполняется, предел времени на ход, предел сообщений в минуту с одного адреса, суточный потолок расхода на модель. При сбое клиент получает честный ответ, обращение уходит менеджеру.
- **Служебные имена.** Имена полей и инструментов из данных до клиента не доходят: ответ с ними возвращается модели, а если она их оставила, имя убирает код.
- **Скидка.** Агент называет цену со скидкой только из ответа `calc_total` или `make_quote`: код не пропустит больше 5%, сколько бы ни попросил клиент или ни передала модель. Обещание скидки больше 5% словами ("сделаем 12%") возвращается модели, а если она его оставила, код заменяет его фразой о том, что такую скидку согласует менеджер. Акцию вендора из справки агент пересказать может.
- **Реквизиты клиента.** ИНН и КПП из сообщения клиента модель не видит: код вынимает их по слову-метке, а ИНН без метки узнает по контрольной цифре, кладет в память диалога и в графу "Заказчик" КП.
- **Чужие инструкции.** Текст клиента и адрес страницы для модели это данные; служебные метки из них вырезаются.
- **Доступ к чужому.** Файл КП открывается только по ссылке с подписью, которую ставит код, или с ключом оператора: номера КП идут подряд, перебором чужой документ не открыть. Переписку отдает только браузер, в котором шел диалог; с чужим номером диалога начинается новый. В панель "Ход работы агента" уходит краткий итог шага, полный ответ инструмента видит только оператор.
- **Знания без данных клиента.** Общий ответ менеджера попадает в знания агента без контактов и реквизитов, вопрос прошлого клиента следующему не показывается.
- **Любой сбой.** Не ответила модель, вернула пустой ответ или упал сам сервер: клиент получает сообщение о передаче, менеджеру заводится обращение с сообщением клиента и его контактом.

### Инструменты

| Инструмент | Что делает |
|---|---|
| `search_products` | поиск по названию, вендору, артикулу или задаче; опечатки, транслит, разговорные названия; если продукт найден однозначно, сразу отдает его варианты |
| `get_product` | варианты лицензий продукта с ценой и артикулом; фильтры по количеству, сроку, типу лицензии и организации, версии, платформе; подсказка, что уточнить; описание продукта со страницы магазина |
| `browse_categories` | категории каталога по описанию задачи |
| `find_analogs` | аналоги из той же категории, по умолчанию российские |
| `kb_search` | справка: получение лицензий, оплата, НДС, документы, возврат, личный кабинет; вместе с ней приходят прошлые ответы менеджеров на похожие вопросы |
| `calc_total` | сумма по позициям |
| `make_quote` | черновик КП в PDF; повторный вызов обновляет тот же черновик |
| `handoff_to_manager` | передать менеджеру со сводкой |

Память: в диалоге агент помнит сказанное клиентом о себе, найденные продукты и показанные варианты; при повторном визите в течение 30 дней видит, что обсуждали раньше. Чат передает адрес страницы, с которой пишет клиент: 31 из 72 обращений без названия продукта написаны с карточки товара.

## Экран оператора

- **Карточка обращения.** Собирается кодом из памяти диалога в момент открытия, модель для этого не вызывается: срочность и срок реакции по теме, данная агентом и запрошенная клиентом скидка (госзакупка и жалоба 2 минуты, скидка и договор 5 минут, остальное 15 минут: по замеру заказчика менеджер сейчас отвечает в среднем через 2 минуты; сроки меняются настройкой), пометки "просит скидку", "госзакупка", "цена по запросу", клиент с реквизитами и контактом, его запрос, показанные позиции, расчет и черновик КП. Менеджер берет обращение в работу или возвращает диалог агенту.
- **Telegram.** Та же карточка приходит в чат менеджеров в Telegram через несколько секунд после передачи, следом файл черновика КП (`app/notify.py`). Ответ реплаем на карточку уходит клиенту в чат сайта, страница подхватывает его без перезагрузки. Пока диалог идет, карточка в Telegram обновляется: новые позиции, сумма, статус. Отвечать клиентам может только чат менеджеров из настройки. Включается ключом бота и номером чата; без них обращения видны на экране оператора.
- **Ответ менеджера.** Уходит клиенту в чат, есть заготовки. Ответ, отмеченный как общий, попадает в поиск: на похожий вопрос следующего клиента агент ответит так же. Модель при этом не переобучается, а данные клиента в знания не попадают.
- **В проверочный набор.** Диалог, где агент ошибся, одной кнопкой становится кейсом: оператор отмечает, как должно было быть, следующий прогон этот диалог проиграет.
- **Экономика, журнал, каталог.** Выгода с допущениями, выгрузка всех диалогов в CSV, состояние каталога и кнопка обновления.
- **Роли.** С ключом оператора экран показывает все и дает действовать. Без ключа он открыт на чтение: почта, телефоны и реквизиты клиентов скрыты, файлы КП не открываются.
- **Диалоги прогона.** Обращения из проверочного прогона подписаны и стоят после живых: в счетчик "ждут ответа" и в просроченные они не входят.

## Данные

**Каталог** (`app/catalog`). Фид магазина на 26.11.2026: 136 290 предложений, 513 категорий, 1 234 вендора, 12 787 продуктов (4 415 линеек программ и 8 372 отдельных товара). С ценой 56 022 предложения, у 80 268 цена 0: агент называет это "цена по запросу". У каждого варианта разобраны срок, пользователи и узлы, ступень количества, тип лицензии, тип организации, версия, платформа. Сборка базы занимает около минуты.

- **Две разметки фида.** Файл из материалов задачи и живой адрес магазина называют параметры по-разному: число пользователей "30" против "от 30 до 30", "Пользователь" против "Конечный пользователь", в живом фиде есть название линейки и артикул для 61 тыс. позиций без него в файле. Сборка читает обе.
- **Обновление без остановки.** Новая база собирается рядом и подменяет рабочую одним переименованием. Подмена отменяется, если в новом фиде меньше 70% прежних предложений или параметры лицензий стали читаться заметно хуже (магазин изменил разметку): чат продолжает отвечать по вчерашнему каталогу, причина видна оператору. Первое же живое обновление в спринте поймало именно такую смену разметки.
- **Ступени количества.** У 23 150 предложений цена зависит от объема закупки, в названии ступень не видна. Фильтр по количеству выбирает нужную ступень.
- **Один артикул с несколькими ценами.** Таких артикулов 827, у 439 различие по параметрам не извлекается: вариант получает отметку, агент показывает вилку и уточняет.
- **Описания продуктов** (`app/catalog/cards.py`). В фиде описания продукта нет: в поле description там параметры лицензии. Заказчик на брифе разрешил брать все, что есть на карточке товара, поэтому текст вкладки "Описание" агент подгружает со страницы продукта при первом обращении к нему и хранит в своей базе. Запросы к сайту идут по одному, не чаще раза в 2 секунды; на отказ сайта запросы останавливаются на полчаса, агент продолжает работать по фиду. Заранее подгружены описания 149 продуктов с наибольшим выбором.
- **Российское ПО.** Номер реестра в фиде есть у 1 208 предложений (20 продуктов). Признак "российский" собирается из номера реестра, веток "(Импортозамещение)" и справочника `data/ru_vendors.txt` на 256 вендоров; справочник составлен вручную по списку производителей фида, это допущение.

**База знаний** (`app/kb`). 366 страниц, 2 171 фрагмент: справка docs.softline.com и 22 служебные страницы магазина (оплата и доставка, правила продажи, контакты, тендеры, акции).

**Переписки** (`docs/chat_analysis.md`). Прочитаны все 495 обращений: 85,5% называют продукт, 42,4% спрашивают цену, КП или счет просят 25,9%, в 21,2% несколько вопросов, 9,5% не знают, что им нужно. Из разбора взяты правила инструкции, темы, которые сразу идут менеджеру, словарь разговорных названий ("кес", "ксп", "астра орел") и проверочный набор.

**Шаблон КП** (`app/quote`). Черновик повторяет шаблон заказчика: шапка, графа "Заказчик", таблица позиций, условия, срок действия. НДС 22/122, позиции с номером реестра идут "Без НДС", позиции с ценой по запросу стоят отдельным списком под таблицей и в итог не входят, позиции не в продаже помечаются для менеджера. Скидка агента видна в документе: позиции стоят по ценам каталога, ниже идут строки "Сумма без скидки", "Скидка 5%" и "Итого". Графа "Артикул" печатается, когда артикул есть хотя бы у одной позиции: в фиде его нет у 22% предложений. Пример: `docs/kp_example.pdf`.

## Проверка качества

- `pytest`: 312 тестов; на чистом клоне без баз заказчика тесты, которым нужны каталог и справка, пропускаются с подсказкой. Каталог и справка на данных заказчика, КП (суммы и НДС пересчитываются в тесте независимо; по напечатанным ячейкам сверяется, что цена на количество дает сумму строки, а столбцы сходятся с итогом), цикл агента на модели-сценарии (проверка цен, пределы, сбой модели, память, скрытие контактов), мост (дежурство, снятие запроса без ответа, ходы разом), сервер и экран оператора (роли, лимиты, заголовки), обновление каталога.
- `eval/cases.jsonl`: 63 проверочных диалога, 57 начинаются с реального обращения из переписок, два повторяют примеры заказчика, два добавлены после брифа (отсрочка и скидка больше 5%; статус заказа и закрывающие документы). `python -m eval.run --min-pass 0.7` завершается с ошибкой, если доля диалогов без ошибок ниже порога.
- По ходу спринта набор прогонялся восемь раз: от 34 диалогов из 61 в первом прогоне до 57 из 63 в двух последних. После третьего прогона правились и сами проверки: девять диалогов они браковали при верном ответе агента (например, не узнавали вопрос о сроке, заданный словом "год").

## Модель

Модель подключается через один интерфейс (`app/agent/llm.py`) и меняется настройкой `LLM_PROVIDER`:

- `openai`: любой сервис с OpenAI-совместимым API, в том числе модель с открытыми весами в своем контуре через vLLM или Ollama;
- `gigachat`: GigaChat API (функции, российская модель);
- `bridge`: мост разработки. Запросы агента складываются файлами, отвечает на них модель в сессии разработчика. Так шли разработка и прогоны: модель Claude Sonnet 5.5, ключа API в этом режиме нет, поэтому токены считаются оценкой.

На демо-стенде отвечает Claude Sonnet 5.5 через тот же мост. Это режим показа, а не боевое подключение: модель работает в сессии разработчика, пока он на дежурстве. Чат и экран оператора показывают имя модели и то, на связи ли она (`/api/health`). Если отвечать некому или ответа нет 90 секунд, клиент получает сообщение о передаче менеджеру, а обращение появляется на экране оператора: так стенд ведет себя при любом сбое модели. В боевом контуре ставится `openai` или `gigachat` с ключом заказчика; цикл агента, инструменты и проверки при этом не меняются. На этих подключениях проверочный набор не прогонялся.

Скорость. 26.11.2026 на финальном коде через чат стенда прошли пять живых диалогов, 13 реплик клиента. От отправки сообщения до ответа: медиана 6,8 секунды, от 4,2 до 10,1. Первый шаг агента (какой инструмент вызван) клиент видит через 2,8 секунды. На реплику пришлось 2,1 обращения к модели, около 3,5 секунды на обращение. Отдельно проверен длинный диалог: 8 реплик подряд в одном диалоге (подбор, сравнение редакций, пересчет на другое количество, скидка, КП, вопрос о получении лицензии). Время и расход к концу не растут: 6-11 секунд и 14-22 тыс. токенов на реплику, выбранный продукт, количество и скидку агент помнит до последней реплики. Это время через мост; экран оператора считает его по живым диалогам стенда (показатель "модель думает на запрос").

Заказчик требований к модели не ставит. Векторного поиска нет намеренно: названия продуктов, артикулы и опечатки лучше ловит полнотекстовый поиск с триграммами и транслитом, а смысловой подбор ("защитить почту") делает модель через категории каталога.

Стек: Python 3.13, FastAPI, SQLite с FTS5 (каталог, справка, диалоги), reportlab (PDF), httpx, snowballstemmer. Интерфейс без фреймворков: HTML, CSS, JS.

## Запуск

```bash
git clone https://github.com/simonsafronov/ai-support-agent && cd ai-support-agent
python3 -m venv .venv && .venv/bin/pip install -r requirements.lock
cp .env.example .env            # вписать ключ модели и ADMIN_TOKEN

.venv/bin/python -m app.catalog.update      # каталог с фида магазина -> data/db/catalog.sqlite, около минуты

.venv/bin/python -m app.kb.crawl build      # справка -> data/db/kb.sqlite

.venv/bin/uvicorn app.web.server:app --port 8000
.venv/bin/pytest -q                         # тесты
.venv/bin/python -m eval.run                # проверочные диалоги, отчет в eval/runs/
.venv/bin/python -m eval.to_stand eval/runs/<прогон>   # показать диалоги прогона на экране оператора
```

Каталог можно собрать и из файла: `python -m app.catalog.ingest --feed data/raw/feed.xml`. Контейнер: `docker compose up --build` после сборки баз (том `./data`, процесс работает не от root, есть проверка здоровья). Настройки с пояснениями: `.env.example`.

Состав поставки: `app/` (каталог, справка, агент, КП, веб), `eval/` (набор и прогон), `tests/`, `docs/` (разбор переписок, питч, пример КП), `data/ru_vendors.txt`, `certs/` (корневые сертификаты для GigaChat API). Данные заказчика (фид, переписки, шаблон) в репозиторий не входят.

## Внедрение

```
 Чат сайта (Webim) --> агент (этот сервис в контуре заказчика) --> модель (GigaChat, свой контур или шлюз)
        ^                   |  каталог: фид магазина, обновление раз в сутки
        |                   |  справка: docs.softline.com и страницы магазина
        |                   v
  ответ менеджера <-- обращение карточкой --> Telegram менеджеров, экран оператора, CRM
```

1. **Чат.** У заказчика чат сайта работает на Webim. Агент принимает сообщение и отдает ответ по HTTP (`/api/chat`); к Webim он подключается как внешний бот через Webim External Bot API: адрес бота и токен задаются в настройках Webim. Адаптер между форматом Webim и `/api/chat` в спринте не делался.
2. **Модель.** Одна настройка: GigaChat, модель в своем контуре через OpenAI-совместимый сервер или внешний шлюз. Для зарубежной облачной модели контакты и реквизиты клиента уже заменяются метками до отправки.
3. **Менеджеры.** Обращения приходят карточкой в Telegram и на экран оператора. CRM или 1С подключаются тем же способом: еще один получатель карточки, цикл агента не меняется.
4. **Данные.** Каталог берется с фида магазина, справка со страниц заказчика. Заказчик задает сроки реакции по темам, потолок скидки агента, ключи операторов и чат менеджеров.
5. **Пилот.** Первые проверки на живом трафике: точное число токенов и время ответа на прямом API, кэш промпта, доля диалогов без менеджера, доля диалогов с КП.

## Не сделано

- Встраивание в действующий чат сайта (у заказчика он работает на Webim) и связь с CRM или 1С: по ответу заказчика не требуются, на стенде свой чат. Как это ложится в контур заказчика, описано в разделе "Внедрение".
- Остатки и сроки поставки в реальном времени: в фиде есть только признак "в продаже" и цена.
- Счет агент не формирует: клиент получает счет-оферту сам, когда оформляет заказ на сайте с оплатой по счету. Агент рассказывает это по справке и готовит черновик КП.
- Фамилию и имя в свободном тексте код надежно не вырезает: скрываются почта, телефон, ИНН и КПП. Для боевого контура с требованиями 152-ФЗ модель ставится российская или в своем контуре.
- Вход оператора по учетным записям: сейчас один ключ оператора на всех менеджеров.
- Кэш промпта в коде не включен: в разделе "Экономика" он посчитан по токенам прогона. Время ответа и точное число токенов на прямом API не измерялись: стенд и прогоны работают через мост.
- Корзина на витрине стенда: КП собирается в диалоге.

Известные ограничения, найденные независимым ревью и живым тестом 26.11.2026 и не исправленные до заморозки кода:

- Об уходе вендора с рынка (Adobe, Autodesk) агент сам не предупреждает: в каталоге такого признака нет.
- Сводка обращения пишется в момент передачи. Если диалог после этого продолжился, в карточке обновляются позиции, сумма и последнее сообщение, а сама сводка остается прежней.
- Клиенту говорится, что менеджер ответит в рабочее время; часы работы агент называет только по вопросу, из справки.
- Сумму, названную клиентом, код узнает по словам вокруг нее; при необычной формулировке агент может получить лишнее замечание и переписать ответ.
- Обещание скидки без процента ("сделаем хорошую скидку") код не ловит: это держит только инструкция.
- Номер из 10 цифр без слова "ИНН", не прошедший проверку контрольной цифры, скрывается как телефон.
- В панели "Ход работы агента" в чате видны срабатывания проверок цены и служебных имен; срабатывание проверки скидки видно только оператору в журнале.
- Описания подгружены заранее для 149 продуктов из 12 787; для остальных первое обращение к продукту идет на страницу магазина и добавляет к ответу около 2 секунд.
